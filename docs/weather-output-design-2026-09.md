# 天气输出信息分层与格式化方案

整理日期：2026-09-14

本文同时区分已经获取、尚未解析、需要新增接口的数据。新接口指相对当前项目接入的新增能力，不代表已经核实全部产品的发布时间或更新日志。公开文档可用不等于账号已开通。

主卡顺序固定为：当前摘要 → 核心天气表 → 降水与体感详情（有数据时）→ 更多气象参数 → 生活指数 → 空气质量 → 来源页脚。空气质量是最后一个业务区块；小时和日级视图也把空气质量详情放在最后。

## 1. 目标

天气消息首先回答三个问题：现在体感如何、今天是否需要采取行动、接下来几小时是否有突发变化。原始 API 字段、供应商解释和扩展查询都应服务于这三个问题，不能因为字段已经取回就全部挤进主卡。

输出遵循四条规则：事实优先；时间明确；单位随字段；来源可追溯。缺失字段不使用 0、晴或估算值填充。降水量 `mm`、降水强度 `mm/h`、概率 `%` 必须分开显示。

## 2. 推荐的四层结构

### 第一层：主卡（默认展开）

只保留地点日期、当前气温/天气/体感、今日最低最高、昼夜天气、湿度风况、降水提示、紫外线、日出日落。主表控制在 6–8 行。

当前“未来 6h 降概”取的是未来六个小时概率的最大值，它是风险提示，不是六小时累计概率。推荐改成“未来6h最高降水概率”。

### 第二层：空气质量折叠卡

标题只显示 `🌫️ 空气质量 · AQI 39 · 优`。点击后显示带边框的紧凑表格：

| 污染物 | 浓度 | 官方分项等级/指数 |
| --- | ---: | ---: |
| PM2.5 | 22 μg/m³ | API 返回值 |
| PM10 | 38 μg/m³ | API 返回值 |
| O₃ | 114 μg/m³ | API 返回值 |
| NO₂ | 11 μg/m³ | API 返回值 |
| SO₂ | 2 μg/m³ | API 返回值 |
| CO | 0.5 mg/m³ | API 返回值 |

当前代码已获取污染物浓度，但模型没有保存每个污染物的 `subIndexes` 和单位。现有“水平”列由本地浓度阈值生成，不应作为可靠官方等级；后续应替换为供应商分项指数，缺失时显示“—”或隐藏全空列。分项指数本身不保证附带类别，不能假定 API 直接返回每项的“优/良”。和风中国 AQI 已采用 HJ 633—2026，应停止用不匹配的浓度阈值推断。

空气质量详情顺序建议固定为：AQI 标准与类别、首要污染物、污染物表格、一般人群建议、敏感人群建议、监测站和数据时间。当前只有一个 `description`，会丢失敏感人群建议。

### 第三层：逐小时与逐日详情

逐小时主表显示时间、天气、温度/体感、概率/降水，必要时同格两行，避免手机六列过宽。详情按“风与体感”“其他气象参数”“空气质量”分成三张窄表，每表最多 4–5 列，不用一张十几列的大表。阵风依赖和风新接口；模型中的 UV 字段不等于旧小时接口真实返回 UV。逐日主表保持天气、气温、降水和 UV；详情显示昼夜天气、昼夜风、昼夜概率，空气质量最后展示。

小时 AQI 已在现有更多指标表展示，小时 PM2.5、日级 AQI/PM2.5 未在对应 Rich 表完整展示。和风中国区明确不提供预报污染物明细，PM2.5 可能依靠彩云补齐；必须允许缺失。已有 AI 输入和外部 JSON 会暴露部分字段，“Rich 没展示”不代表项目完全没使用。

### 第四层：行动型专题

降雨图、温度图、潮汐、台风、AI 日报和预警保持独立按钮或命令。它们数据量大或使用频率低，不应争夺日常天气卡首屏空间。

## 3. 分级规则

- 绿色表示优、适宜、低风险；必须同时保留文字。
- 黄色表示需要留意，例如降水概率较高或 UV 强。
- 橙色/红色表示需要采取行动，例如较差空气、强降水、大风或正式预警。
- 灰色只表示暂无数据，不能表示空气质量差或无降水。

颜色不应由污染物浓度自行推断。空气质量使用 API 的本地 AQI 等级；预警使用预警等级；UV 使用供应商分级；降水把概率和强度分别表达。QAQI、当地 AQI、中国 AQI 的数值不能直接横向比较。

## 4. 实施优先级

1. 本轮已完成：空气质量三列表格增加边框，保留紧凑和无条纹底色。
2. P0：将“未来6h降概”改名；严格区分彩云逐日降水强度、和风逐日累计量和概率单位。
3. P1：扩展 `AirQuality` 保存 AQI 标准、分项指数、单位、健康影响和敏感人群建议。
4. P1：小时详情增加 PM2.5、阵风、UV；逐日详情增加 AQI/PM2.5。
5. P2：评估迁移到和风 `/weather/v1/current|hourly|daily`，先验证权限、计费、缓存和回退，再切换默认来源。

默认天气卡应保持一屏主要信息；字段缺失时不显示；每个降水值必须能从标签判断 `mm`、`mm/h` 或 `%`。

## 6. 和风新天气接口的展示收益

本轮会话已读取新接口官方字段页，当前代码仍调用 v7 城市/格点天气，尚未接入下列天气 v1。

| 接口 | 相对当前接入的价值 | 展示决策 |
| --- | --- | --- |
| `/weather/v1/current/{lat}/{lon}` | 当前阵风、当前UV、露点，独立一小时累计量/降水强度/类型，全球1km坐标数据 | 当前实况或详情；大风风险突出阵风，常态不挤主表 |
| `/weather/v1/hourly/{lat}/{lon}` | 原生小时体感、阵风、UV、雨雪冰混合类型，最长240h | 小时详情和短时变化；不把240行一次展开 |
| `/weather/v1/daily/{lat}/{lon}` | 昼夜最高最低温、最大阵风、降水量/概率；晨昏、太阳中天等 | 昼夜表；晨昏放天文详情，摄影场景再突出 |

新 daily 最长10天，旧城市 daily 可达30天。不能无条件替换而使当前15日能力退化；实施时决定保留长程来源或按范围路由。新接口单位有 m/s、m、0–1，不能直接套旧 v7 的 km/h、km、0–100 解析。和风昼夜07–19/19–次日07，彩云08–20/20–次日08，跨供应商补齐必须保留窗口，不能合并为同一统计时段。

## 7. 彩云公开新产品与当前套餐

v2.6仍有未用尽的字段，优先复用综合响应。当前文档也有 `dailystart=-1`、通常15日/最高360小时参数范围；这是可请求范围，项目仍为72h/15d，实际以套餐截断和响应为准。回退一天不等于历史观测，不应替代和风昨日实测。

彩云官方目录另列v3丰富生活指数、空气质量预报、预警/CAP/Webhook、朝晚霞、潮汐海浪、天文，以及雷达卫星等产品。这些是公开目录能力，未核实发布时间及当前Token权限，不能声称已可用。

- 朝晚霞、雷达短临：对户外/降雨专题有潜在价值，套餐确认后再评估。
- 生活指数、台风、潮汐：已有和风实现，新增彩云端需要明确覆盖或质量收益。
- CAP/Webhook：主要改善后台预警接入时效，不能当成新增主卡行。
- 土壤、高空、光伏辐射：日常天气卡价值低，保持专题边界。和风独立太阳辐射曾因成本移除，不自动恢复。

## 8. 展示前必须修正的数据语义

1. 彩云逐日avg在metric:v2下仍为mm/h。现有昼夜字段只带一个日级precip_kind，融合和风后会错用mm；给每个时段值保留自己的单位、来源和窗口。
2. 彩云当日temperature.avg表示当前整点至日末平均温度，不是完整日均温；当前“日均温”标签应按来源/日期改为“今日剩余时段均温”。未来日与昼夜窗口另行标注。
3. AQI标准、单位、显示值、官方分项指数一起保存；未来空气趋势应同标准比较，缺少标准元数据时不推导优良天数或风险阈值。
4. 两家响应及各组件缓存时间不同。页脚不得让用户误以为所有指标同时更新；无观测时间时可显示获取时间，并明确名称。
5. 风险提示可以由原始序列做最大值/差值统计，但“最适合运动时段”等综合结论需明确规则或放AI建议区，不能伪称供应商事实。

## 9. 下一批建议范围

先修正单位、AQI元数据与日期匹配，再补同响应中的原生字段和分组展示；最后单独迁移和风天气v1并验证权益。这样补信息不会使错误标签更醒目，也不会无意增加每次请求成本。
